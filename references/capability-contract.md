# Harness Capability Contract

> This is the **single interface** between the `harness-coding` skill and any execution harness. The methodology body references only capability names from this contract and never references concrete tools, CLIs, or frameworks.
> Each harness maps capability names to its own implementation through one adapter layer (filled in as `adapters/<harness>.md` per `adapters/_adapter-template.md`).

---

## 1. Design Principles

1. **The capability name is the contract**: the body uses only capability names (e.g. `read` / `run_command`), never concrete nouns like a `Read` tool, `Bash`, `Agent`
2. **Required vs optional**: if a required capability is missing the skill cannot work — prompt to complete the adapter layer; if an optional capability is missing, degrade per the degradation rules (every optional capability has one)
3. **Single source of truth**: onboarding a new harness only requires adding one adapter file; the methodology stays unchanged
4. **Artifacts as state**: there is **no report-writing capability**. Task state lives in plain markdown artifacts under `specs/<slug>/` (`spec.md` / `plan.md` / `tasks.md`; 🟡 single-file: `intent.md`), history and concurrency live in git. The final summary is a chat reply; the on-demand traceable view is generated by `scripts/derive-report.py` and is never persisted

## 2. Capability List

### Required capabilities (7; missing → skill unusable)

| # | Capability | Signature | Semantics |
|---|-----------|-----------|-----------|
| 1 | `read` | `read(path) -> str` | Read a file's content |
| 2 | `write` | `write(path, content) -> void` | Create / overwrite a file (read before overwriting an existing file) |
| 3 | `edit` | `edit(path, old, new) -> void` | Exact replacement; `old` must match uniquely, else raise |
| 4 | `glob` | `glob(pattern) -> list[str]` | Pattern-match file paths |
| 5 | `grep` | `grep(pattern, path?) -> list[Match]` | Content search, matches with file:line |
| 6 | `run_command` | `run_command(cmd) -> Output` | Run a shell command; stdout/stderr/exit_code. The only channel for quality gates |
| 7 | `ask_user` | `ask_user(questions[]) -> answers[]` | **Batch** question primitive: each question presents 2~4 mutually exclusive options, recommended one first. Used for intent-unclear verdicts, clarification gates, architecture decisions, merge method |

> **`ask_user` batch semantics**: the clarification gate requires all questions in one round — never serial single questions spread across turns. If the harness primitive only supports a single question per call, degrade to **serial asks within the same clarification round** (one user interaction session, no spread). Headless harness (no human in the loop): pick the most conservative option (fewest irreversible side effects), record `⚠️ unable to ask the user; decided on the conservative option` — never pretend the user confirmed.

> **`edit` composition semantics**: when no dedicated primitive exists, a `read`+`write` composition (read-all → replace in memory → write-all) satisfies the requirement; preserve the **unique-match** rule — never silently fall back to first-match-wins; raise and let the caller narrow the context.

### Optional capabilities (5; missing → degrade per the rules)

| # | Capability | Signature | Semantics | Degradation rule |
|---|-----------|-----------|-----------|------------------|
| 8 | `spawn_agent` | `spawn_agent(role, prompt) -> AgentReport` | Spawn a sub-agent, collect a structured report | Orchestrator executes the role inline (serially), responsibilities unchanged |
| 9 | `create_branch` | `create_branch(name) -> void` | Create an isolated branch/worktree | Work directly on the main workspace, annotate `not isolated (no branch capability)` |
| 10 | `check_command` | `check_command(cmd) -> bool` | Verify a command is available | Run once via `run_command` to decide |
| 11 | `find_skill` | `find_skill(query) -> list[skill]` | Search the **local skill library** (after classification, before drafting); a hit is loaded as a conditional skill | Fall back to the **static conditional-skill mapping table** in the adapter (§4) |
| 12 | `web_search` | `web_search(query) -> results` | Verify external knowledge the repo cannot resolve (dependency versions / compatibility / API behavior) | Record `not verified online` in the spec's Assumptions section; flow not blocked |

> **`web_search` discipline** (all three mandatory): results entering a spec must carry **source + retrieval time**; acceptance criteria (AC) must be **locally executable** — a web-search conclusion never becomes an AC; restraint — if the repo can answer it, do not search the web.
>
> **`find_skill` semantics**: the skill library is the harness's installed skill packages (frontmatter `name` + `description`). No search primitive is needed to satisfy the *semantics* — listing skill directories via `glob` + reading frontmatter via `read` is a valid implementation.

## 3. Quality-Gate Abstraction (not a capability, a protocol)

A fixed call sequence over `run_command`:

```text
lint → format --check → type check --strict → test (including the coverage threshold)
```

- Concrete commands are project-defined (e.g. `ruff check .` / `ruff format --check .` / `mypy --strict .` / `pytest --cov=...`), written into the adapter's gate table
- Per-task gates run after each implementation task. **Incremental per-task mode (🟡/🔴)**: lint / format / type always run in full (they are fast); `test` may run the **affected subset only** (e.g. `pytest tests/<module>/ -k <scope>`) — the full suite is mandatory at close-out re-verification. 🟢: lint + format mandatory, type/test on demand with reason recorded (unchanged)
- **Gate N/A protocol** — a gate that does not apply is **never silently skipped**. Skipping requires a pairing:
  1. **Declaration** in the spec's (🔴) or intent's (🟡) `## 门禁豁免` section: `- GATE-NA(<gate>): <reason + scope>` (e.g. "docs-only change, no code to type-check")
  2. **Reference** at the point of use: the task's pasted output states `GATE-NA(<gate>): declared in spec` instead of that gate's output
  `artifact-check.py` verifies every `GATE-NA(<gate>)` used in tasks has a matching declaration; an undeclared skip is a validation error
  **Scope semantics (mandatory)**: each declaration states its scope — **chain-wide** (e.g. "project has no type system") or **task-scoped** (e.g. "T3 touches only SQL"). A chain-wide exemption also applies at close-out re-verification; a task-scoped exemption does **not** — the close-out full run still executes that gate. When in doubt, treat the exemption as task-scoped (safer: the close-out run decides)
- **Coverage threshold source**: the threshold is **project-declared** (e.g. `[tool.coverage.report] fail_under` in `pyproject.toml`, `coverageThreshold` in jest config) and referenced in the adapter's gate table. If the project declares none, the coverage sub-gate is **not enforced** — plain test pass/fail suffices; never invent a number, never block an old codebase's patch on an unreachable whole-repo threshold
- **Behavior-preserving refactors (🔴)**: when the spec marks the change behavior-preserving (refactor), the **plan must first build a characterization-test baseline** (tests that pin current behavior), and at least one AC must be "baseline tests pass unchanged". The test gate then runs baseline + new tests — this is the refactor's equivalent of a regression gate
- Any failure → locate the root cause → fix → re-run from the failed gate; never delete assertions or loosen existing ones for a green light

## 4. Role Abstraction (optional `spawn_agent` capability)

| Role | Input | Output contract | Artifact home |
|------|-------|-----------------|---------------|
| `explorer` | Recon target + scope | Locations / call chains / reusable patterns / open questions (with file:line) | `spec.md` Background section (**replace** the placeholder, not append) |
| `implementer` | A task with a clear location | Change list / verification results / self-check / remaining risks | `tasks.md` checkbox + pasted gate output |
| `reviewer` | Review scope (diff/file list) | Graded Findings (`R<n>` tagged `resolved` / `open`, level blocker/major/minor) | `tasks.md` (🟡: `intent.md`) `## Review` section |

> Without `spawn_agent`, the orchestrator plays the role itself under the same input/output contract (dispatch templates in `templates/`).
> **Closing rule**: a `blocker`/`major` finding left `open` makes closing illegal — review rejection mechanically returns to implementation.

## 5. Degradation Rules Summary

| Missing capability | Behavior | Annotation |
|--------------------|----------|------------|
| `spawn_agent` | Orchestrator plays the role inline | `no sub-agent, inline execution` |
| `create_branch` | Change directly on the main workspace | `not isolated (no branch capability)` |
| `check_command` | Run once via `run_command` | none |
| `find_skill` | Static conditional-skill table (adapter §4) | none |
| `web_search` | Record `not verified online` in spec Assumptions | none |
| `ask_user` (headless) | Most conservative option, recorded | `⚠️ unable to ask the user; decided on the conservative option` |

## 6. Onboarding a New Harness (Adapter Checklist)

1. Map each of the **7 required capabilities** to that harness's tools/primitives (fill-in table in `adapters/_adapter-template.md` §1)
2. Copy and generate `adapters/<harness>.md` per the template: capability table (7+5) + quality-gate commands + role mapping + conditional-skill mapping + degradation declarations; delete the template's "how to generate" section
3. If a required capability cannot be satisfied → annotate "unsupported capabilities" at the top of the adapter; the skill continues per the degradation rules
4. Run one lightweight requirement end-to-end (e.g. fix a typo): the 🟢 channel must complete **without creating any new file**; then run one 🔴 sample to verify artifacts + `artifact-check.py` pass
